# MX251 后续开发约定

依据用户 2026-11-09 的目标，以下作为后续开发与验收口径。

1. 优先完成官方试验箱 / STC-Link1D 的下载协议研究与独立脚本，取得可重复的构建—下载—实测通道。
2. 中期完成原 AI8051 SDK 的 120% 承诺。先找回原冻结工程集、Keil 基线、已有成绩和未完成项；不得换成缩小的 SDK 或只选容易通过的样例重新宣布完成。2026-11-13 曾按用户要求暂排除 p108，随后修复入口并按双方同源修正输入重新纳入。当前统一 75 项体积结果为 75/75 ≤120%、64/75 ≤110%；完整工程耗时仍未验收。原始冻结报告及中间 74 项报告保留，输入修正与范围变化不算编译器收益。当前名单与配置见 [75 项基线](ACTIVE-SDK-COHORT.md)。
3. 最终每个纳入验收的完整工程，生成代码体积与同条件运行时间分别不超过 Keil C251 的 110%。体积与时间不能互相抵扣，也不能用平均值掩盖单项不达标。尚未建立可比基线的结果记为未知。
4. 除性能外，达到实际工程研发所需的基本水准：正确的 ABI/跨文件调用、中断、volatile/外设访问、地址空间、启动与运行库、链接重定位、资源边界、可诊断失败，以及稳定的正常 CLI/CMake 构建入口。
5. 目标是 MX251 编译能力；允许必要且清晰记录的兼容适配，不通过大幅重写 SDK、手工替换关键算法或按项目/函数名特判来制造成绩。
6. 先做可行性和收益判断。复用输入与实现未变的既有证据；针对新机制和实际影响范围验证，不反复重跑同一矩阵。优先跨一批工程有效的通用收益。按用户补充要求，验证足够就提交，不默认扩大矩阵；沟通先讲收益和进度，减少防御性措辞与无助决策的细节。
7. 若现有结构形成可量化瓶颈，允许重构所需中端/后端。先用代表性热点、资源/成本模型和失败案例证明原因，再实施；重构本身不等于验收完成。
8. 严格 Git 纪律：脏工作区先保留；独立工作树和 `codex/` 分支；只暂存本任务文件；按可评审范围提交；检查差异与相关验证后提交。不夹带用户改动，不重写既有历史，不把原始硬件身份、私人 SDK 或大型抓包混入公开源码。推送/发布单独按用户要求处理。
9. 用户已授权本项目所需的全部硬件操作；需要下载固件时直接执行，无需再次询问。测试结束保留最后下载的固件，不再自动恢复原固件，以节省时间。
