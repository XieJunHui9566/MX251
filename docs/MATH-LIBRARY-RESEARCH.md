# 数学库差距与优化方向 — 2026-11-13

本轮只研究。建议下一轮先打通**普通 C 浮点位型与寄存器传递**，同时让 `fabs/frexp/ldexp` 等基础函数采用同一套原生表示；随后集中改造**多项式调用链与三角函数约简**。单纯重编库、继续微调平方根和除法，不是当前主要收益来源。

## 2. 同源重编库只能拿到小收益

现用归档有 66 个成员，由旧编译器 `25d144e9…` 生成；新基线编译器为 `4e6a7d78…`。使用仓库原有 `BuildNativeFloat.py`、原始源码与原始参数做一次隔离重编：

- 66 个原始 REL 均产生；65 个成员完成原构建配方检查。
- `sqrt_domain` 的检查要求汇编文本 `(_errno)`，新编译器输出 `(_errno+0)`；两者原始对象大小均为 10 B。构建配方没有改动，没有生成可发布的新库。
- 全库 CODE+CONST **15,795 → 15,563 B，减少 232 B / 1.47%**。
- Math123 实际选中的 17 个成员合计只减少 **40 B**：sincos −15、tancot −18、sqrt −7。该数是对象成员之和，未作为替换库重链接后的整工程收益。
- `_fsadd/_fsmul/_fsdiv` 已是手写原生叶汇编，分别 **442 / 400 / 414 B**；换 C 编译器不会改变这三份实现。

因此不值得为这 40 B 单独启动一轮全面验收。下一轮做结构性改动时一并更新构建配方与库来源记录即可。

## 3. 通用编译能力仍有一块明确空间

本轮 Math123 的普通 C 包装函数已经进入宽后端，旧报告的“浮点栈调用不能迁入”不是这里的当前原因。当前问题是局部 union 的整数/float 位型转换仍经栈逐字节存取：

| 形态 | 数量 | 单函数编码大小，链接后处理前 | 单函数局部栈字节 MOV |
| --- | ---: | ---: | ---: |
| float 加/减/乘/除包装 | 4 | 141 B | 24 |
| sqrt/sin/cos/tan/atan 包装 | 5 | 97 B | 16 |
| 合计 | 9 | **1,049 B** | **176** |

这 176 条指令在 LST 中合计占 **686 B**（158 条为 4 B、18 条为 3 B）。它们不是源程序的 volatile 局部对象；局部对象访问仍带 union 表示访问的字节事务标记。`math_b` 本身确为 volatile，全局读取必须按其实际访问语义保留。

现有 `wide_private_union_prepare/finish` 能识别部分完整 4 B 私有对象，但还受 `MX251_PRIVATE_UNION_WORD` 实验变量控制。普通构建不会自动把这些对象变成纯寄存器表示。新后端已能找到对象位置，所以应在这个基础上完成通用对象值传播和位型转换，而不是再做一套按函数名称匹配的补丁。

**方向 A：完整的 32 位对象表示通道。** 对地址未逃逸的局部 union/完整位型搬运建立显式表示操作；把 float/int 的同宽位型转换与数值转换区分开，跨普通函数调用保留标量值，清除不再需要的栈对象。先复用现有对象识别，再扩展普通 C 的前后端连接。

仅把这些局部访问从字节换为双字节，按静态数量估算就有约 0.3 KB 的空间；完整值转发还有空间。**这是机会量，不是已实现节省量**，后续以最终 HEX 与耗时计数。相同机制可用于协议解析、传感器算法、控制代码和数学库本身。

**方向 B：基础数学函数一起迁移。** `fabs/frexp/ldexp/floor/ceil/modf` 六个成员现有 2,054 B。其中 `ldexp` 是纯整数位操作，却在诊断汇编中有 361 条指令、213 条 MOV；`frexp` 有 188 条指令、124 条 MOV，并出现 4 个 `__gptrput` 调用点。让这些函数使用原生整数位型核心和清楚的参数/返回接口，可以同时降低 exp、log、pow、反三角、双曲函数的依赖成本。

这两项适合一次推进：解决普通 C 的表示搬运，再使用同一能力生成运行库。不能为了拿到好汇编要求 SDK 使用特殊整数替身函数。

## 4. 数学库自身的结构优化

### 从 Keil 能确认的事实

本机历史 Keil Math18 的 MAP 显示共享入口：`?C?FPGETOPN2?`、`?C?FPRESULT?`、`?C?FPRESULT2?`、`?C?FPNANRESULT?`、`?C?FP2SERIES?`、`?C?FPSERIES?`。数学调用共用操作数处理、结果处理及级数求值模块，具有明确的共享结构。

同一 MAP 的 `?C?LIB_CODE?` 段合计 1,550 B，**包含整数运行库**，不能称为纯数学库大小。Keil 的 cos 包装 LST 仍保留局部 union，但使用 WR 宽访存，单个包装为 53 B；因此 Keil 也不是必须完全消除对象才能获益。这份 AI8051U 静态 MAP 用于结构对照，不是新的 STC 运行成绩。

可借鉴的是共享结构与数据传递方式。本轮没有从符号名称推定 Keil 使用某一阶数或某一具体近似公式。

### 方向 C：共享多项式调用链，减少反复保存与归一化

新编译器重编的 sincos 成员仍有 68 条 PUSH/POP。其 Horner 链在连续乘加之间反复保存同一个变量、交换 DR4/DR12，并重新装载立即数。exp 有 162 条 PUSH/POP，asincos 有 112 条；这些都是静态条数，不是动态周期。

下一轮应把“寄存器使用说明 + 连续乘加调用 + 系数访问”作为一个库内调用组处理，比较两种实现：

1. 保留逐次舍入顺序，由编译器跨调用保留多项式变量，使用库的实际寄存器读写信息。
2. 对重复形态提供小型共享求值核心和系数表，减少每个函数展开的调用准备代码。

先从 sin/cos 与 exp/log 两组取得共同收益。是否共享循环、是否使用专门的乘加入口，要看空间与时间同时变化；不能把普通 `a*b+c` 默认为一次舍入的 FMA。

### 方向 D：余弦优先的三角约简

当前 cos 先对 `abs(x)` 加 pi/2，再走 sin/cos 共用约简；相对 sin 多了浮点操作，历史时间差距明显。tan 则使用独立的 224 位 2/pi 全范围约简，已经有原生乘积与分数处理核心。

值得做的是：常用小输入直接进入适当的 sin/cos 多项式；中等输入共享较短约简；大输入复用已有精确约简基础。sin/cos 需要商模 4 的完整象限，当前 tan helper 只返回奇偶，不能直接复用旧接口就宣布完成。

这项可同时改善 cos 时间、多个三角函数组合的体积和 sin/cos 的有效输入范围。现有 sin/cos 已共享多项式、tan/cot 已共享核心，不能把已有共享再次记为未来收益。

### 后续候选：共享分类和结果打包

目前 add/mul/div 都是独立叶函数，分类、次正规数、舍入和结果打包各自存在。Keil 的共享入口说明此方向值得保留，但拆出 helper 会增加调用/寄存器保存成本。优先共享实际重复且执行频率低的块；先完成表示通道与多项式调用组，再决定是否改动这三个算术核心。当前不承诺可省多少字节。

## 5. 功能、精度与使用范围的缺口

| 项目 | 当前源码/归档事实 | 后续处理 |
| --- | --- | --- |
| `fmod` | 安装的 Keil `MATH.H` 有入口；MX251 原生 math.h、源码和 66 成员归档没有 `fmodf` 实现/导出 | 补一个通用 binary32 余数接口，并接通常用头文件 |
| `powf` | `y==0/1` 之后，所有 `x<=0` 返回 0；`powf(-2,3)` 返回 0 | 负底整数幂、零底负幂等应列入工程能力补齐 |
| `logf` | `x<=0` 设置 EDOM 并返回 0；正无穷会进入当前通用公式 | 明确零、负数、Inf、NaN 的结果及 errno；不要用速度掩盖数学行为变化 |
| `floor/ceil/modf` | 先转换到 32 位 long | 超出 long 域的有限 float、Inf/NaN、符号零缺少完整处理；用位型算法可兼顾功能与体积 |
| 整数转 float | `u2f_kernel.inc` 保留不精确时幅值向上的旧政策；16777217 得到 16777218 | 与最近偶数舍入不同，应统一常量折叠与运行时契约，独立记录语义修正 |
| sin/cos | 当前 `YMAX=12867`，超限返回 0/ERANGE；cos 的预加 pi/2 影响边界 | 扩展约简时一起解决，不宣称当前支持全部有限 binary32 |
| sqrt / NaN | 负非零返回 0/EDOM；NaN 位型原样返回，而 add/mul/div 会 quiet NaN | 共享分类器之前列清不同契约，不能按名字直接合并 |
| double | 当前这一条库路径为 binary32 | 与 Keil 可选 binary64 是独立能力差距；本轮先比较相同的 32 位配置 |

以上不是本轮新增的硬件失败报告；是当前源实现、头文件和库符号的静态核对。`powf(-2,3)` 为源码可直接确定的行为，其余未运行的新边界不能报作本轮板测结论。

Keil 的官方说明确认其采用 IEEE-754 数字表示；这本身不证明所有 libm 函数都正确舍入。[浮点表示说明](https://www.keil.com/support/docs/531.htm)。C251 还可选 64 位 double，浮点比较默认先舍入最低 3 位；新比较必须记录这些设置，不把不同精度/比较策略混在一起。[C251 编译选项](https://www.keil.com/support/man/docs/uv4cl/uv4cl_dg_c251.htm)。

## 6. STC-IDE 值得借鉴的部分

冻结的官方 STC-IDE 编译器中，AI8051U 标记 `tfpu=true`，STC32G12K128 标记 `tfpu=false`；二者均有 MDU32。浮点硬件发射条件为目标具有 TFPU 且 `mathLib != soft`，所以 AI8051U 默认 `mdu32` 配置也可能走 TFPU，不能只看选项名字就认定是软件浮点。

当前 MX251 TargetContracts 没有对应 TFPU 路径。**可增加目标能力驱动的 TFPU 数学实现**，对 AI8051U 的工程价值可能很高；它与软件库分别比较，并保留 STC32G 的软件路径。当前只确认官方代码中的能力声明与发射条件，没有新测硬件时延、指令语义或中断行为。

官方软件 libm 并非所有算法都更适合照搬：冻结源码中的 sin/cos 都计算正弦和余弦多项式，tan 再调用 sin 和 cos 相除；exp/log 使用多次除法的级数公式。源码结构可以分析，但未经同条件编译和数值核对，不能据此宣布其更快、更小或更准确。官方 `pow` 已有更多特殊输入分支，可作为覆盖范围的对照。

因此本轮软件主线仍以通用表示、库内调用和约简结构为先，TFPU 作为单独目标实现排期。

## 7. 下一轮一次推进的范围

建议先做 **A+B：普通 C 的浮点位型表示/传递 + 基础数学函数原生化**。这一轮不再拆成每个 MOV、每个函数一次提交/验收：

1. 把已有完整 4 B 私有对象识别接入普通构建，形成可见的位型和值传播；覆盖 math123 普通包装与独立 C 调用样例。
2. 用相同后端能力生成 fabs/frexp/ldexp，并一起处理 floor/ceil/modf 的范围问题；保留兼容的公开接口。
3. 提供运行库参数、返回、寄存器及内存影响信息，让连续数学调用可以使用准确的调用代价。
4. 再用同一基线判断 C+D 的联合收益；若主要耗时仍在约简，直接推进 cos 与通用三角约简，不回到逐条压指令。

已有浮点算术内核字节未变时复用其证据。新一轮只运行受影响的数值边界、ABI 调用以及 Math18/123 完整工程；不因修改数学库重跑与之无关的 75 项。新 compiler 与 Keil 的 Math18 同条件板测可以更新 110% 时间距离；Math123 保留缺少合格整组 Keil 分母的事实。新增 exp/log/pow 覆盖要与原样例分列，不能靠增删输入改变历史分母。
