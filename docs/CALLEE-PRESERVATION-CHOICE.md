# 调用保存与后端选择

2026-11-13，实现 `68fa8be`，分支 `codex/callee-preservation-choice`。

全部 75 项由同一编译器构建：**75/75 ≤Keil 120%、65/75 ≤110%**。相对通用下标地址生成版，3 项缩小、71 项相同、1 项变大，净减少 **106 B**。合计 **191616 / 192049 B（99.77%）**。

## 问题与改动

构建器已经按调用点的保存成本选出被调者保存寄存器组，宽后端也已输出对应的 PUSH/POP。随后比较两个后端时，原先只比较单个函数体；旧后端函数体较短，就可能替换掉带保存方案的宽后端。最终调用分析会正确识别这个变化并恢复调用方保存，但原先估算的调用链收益也随之丢失。这是成本选择问题，本轮没有把它认定为旧版算错结果。

`ralloc.c` 增加一个选择规则：已成功生成且带有实际 `mx251-callee-preserved` 标记的宽后端函数，保留该实现。没有这种保存方案的函数仍按原来的双后端比较规则选择；不支持宽后端的函数仍走原来的回退路径。最终 ASM/REL 的寄存器效果和保存指令分析保持原有流程。

本轮只改后端选择，并增加定向测试。没有改 SDK、ABI、寄存器分配器或构建器的成本算法，也没有按工程或函数名匹配规则。`MX251_PRESERVED_BACKEND=0` 可用于研究对照，恢复本轮改动前的选择。此前文档中“旧后端可以替换被调者保存实现”的描述是历史行为；本轮对已成功输出保存实现的函数改变了这一点。

## 验证与实板

- small/large × speed/size 四种配置，比较父版、新版关闭、新版启用、无保存请求的父版/新版五种情况。关闭时指令与父版一致；无保存请求时指令也与父版一致；启用时原先被旧后端替换的函数保留宽后端 PUSH/POP。
- 既有被调者保存测试四配置通过，覆盖栈对象、取地址参数、递归以及 ABI2/ABI4；12 个控制流/栈案例与 112 个编译函数的保存分析通过。
- 统一矩阵复用同一编译器、配置下已完成的四个代表工程，只补建其余 71 项。最终 75 项编译器和构建脚本记录一致。

AI8051U 实板上父版和新版各 **128/128** 组通过。相同源测试固件 **1226 → 1210 B**。测试使用原绘图线段/矩形函数，通过两次调用的像素包装函数生成结果轨迹；Python 独立计算光栅步进和轨迹。构建器自动选择保存组，测试中没有强制指定保存方案。

这个实板用例的 `LCD_DrawPoint` 确实从父版的旧后端切换到新版保留的宽后端，覆盖了此次改动路径。最初构建的 `fixture-parent/new` 没有触发选择差异，未用于实板结论；最终证据来自 `fixture-wrap-parent/new`。
