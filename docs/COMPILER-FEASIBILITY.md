## 判断

**2026-11-09 后续修正：** 找回归档后确认普通函数自动迁移 ABI4、调用保存打包及平坦指针转换都已有未通过收益门槛的整工程实验。新增四槽布局的最终调用点核算也表明，其增量主要集中于 TFT，对三个 USB 代表工程几乎无覆盖。当前先不实施新全工程 ABI，转向已有 ABI 的调用成本与宽后端回退；详见 [调用布局主线筛选](CALL-LAYOUT-FEASIBILITY.md)。以下保留首轮判断的依据，不能将其原型顺序当成尚未检查的空白方向。

现有证据不足以证明 MX251 最终一定能达到双 110%，也不足以断言整个架构必须推倒重写。已能确定的是：已有静态局部变量和 CODE 指针压缩的小范围收益，不能填平代表工程的差距。下一项值得投入的是**明确版本的原生调用约定、寄存器参数与调用保存的协同原型**；局部存储另行选择，不把关闭 `stack-auto` 当作完成方案。

## 先沿用的事实

旧 p080 的非 stack-auto 实验仅分编译单元累计少约 2124 B；整工程链接因 DATA/OSEG 容量和运行库参数符号不匹配失败。这不是可交付的完整工程收益，也不能与其他实验的节省直接相加。即便暂按 2124 B 作乐观上限，距离 p080 的 110% 线仍有约 1193 B，需要其它通用收益。

## 源码核对后的关键修正

- `src/mcs251/gen_lower.c.inc` 的 `aopArg()` 表明：普通 ABI2 仅第一个非结构、非 bit 标量走寄存器；ABI4 才有两个独立原生槽，第三个及以后仍不走寄存器。
- `src/mcs251/main.c` 的 `mcs251ValidateNativeAbi()` 允许原生 ABI 配合重入/栈局部，但当前要求显式函数声明，拒绝全局 ABI3/4 切换。不能简单把全 SDK 编译选项改成 ABI4，或者认为关闭 `stack-auto` 就会自动变成 Keil 的多寄存器参数约定。
- `src/SDCCmem.c` 分别处理 `allocParms()` 与 `allocLocal()`，但二者均受 `stackAuto`/重入条件影响。旧 overlay 实验同时改变了参数存放和局部存放，无法把全部减少量归因于寄存器传参。
- 现有运行库、跨文件声明、间接调用以及普通/宽后端回退均绑定调用约定。新约定必须进入类型、对象/构建契约与库选择，不能只改 caller 的 PUSH 或局部私有寄存器名。
- 目标配置中的 `qualifiedMemory` 是当前验证窗口，不是芯片全部容量。EDATA 的候选空洞必须结合实际栈预算、全局分配和启动再证明；历史估计不能直接授权占用某段 RAM。

## 原型范围与停止条件

优先做一个独立版本的调用布局描述，供 caller、callee、返回值、寄存器别名与成本计算共用；保留栈局部语义，先验证多参数小函数在重入情况下减少搬运/压栈的收益。直接调用、间接调用、外部/运行库边界要有同一类型规则。未知或不支持的类型采用明确的旧 ABI 边界或拒绝，不能生成混合约定的对象。

原型先覆盖一个绘图类完整工程和一个 USB/分发类完整工程，沿用已冻结源码及基线。只有在正常构建入口取得明显最终字节收益，且没有把成本移到热路径/栈资源后，才扩大范围或配套重编运行库。若只能重复已有静态局部方案的百字节收益，或只对手工标注 SDK 函数有效，停止扩展，回到调用点、live range 与 spill 归因。

确需新 ABI 时保留旧 ABI2/4 路径，使用新版本和新运行库目录；不静默替换已有二进制契约。必要检查集中在跨文件、函数指针、重入/ISR 可达、混合宽度和负成本案例。本次没有重跑未变化的旧机制。

这是下一步实现选择，不是新的性能达标结论。最终仍需统一工具链下逐工程双 110% 以及实际工程正确性验收。
