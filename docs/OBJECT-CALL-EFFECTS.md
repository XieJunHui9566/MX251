# 对象信息接入调用效果：2026-11-09

这次把编译器已有的对象区域和大小传到调用效果分析。普通 DATA / BIT 对象写入不再使整个函数变成“改写全部寄存器”，跨文件调用和上层调用者可以继续计算实际寄存器写集合，现有分配器及调用保存代码由此省去不需要的 PUSH / POP。

这是统一后端的第一层数据接口。当前仍使用已有汇编效果扫描和两套后端；没有把这一步称为完整 Machine IR 重构，也没有调整分配权重、扩大 ABI 参数寄存器或修改 SDK。

## 实现

- `SDCCglue.c` 在真正分配存储的 `.ds` 后输出 `mx251-object schema=1`，包含符号、`data` / `bit`、对象大小。extern 声明、绝对地址和自定义 DATA 段不冒充普通已分配对象。
- `CallClobberFeedback.ps1` 建立各单元的对象表，用实际 `.rel` 定义绑定导出对象，保留同名 static 的单元作用域。函数分析和普通后端的实参设置分析共用该对象表。
- 对 `symbol + offset` 保留对象身份、偏移和访问宽度；不会为尚未链接的符号编造地址。普通 DATA 的结论建立在链接器保留 bank 0、DSEG 分配到低 128 字节的现有规则上。
- 校正 DATA `0x08..0x1f` 的物理别名：它们是 bank 1..3 的 R0..R7，并非 CPU 高寄存器 R8..R31。bank-0 函数写这些 RAM 字节不会改写高寄存器。A/B、PSW、切换寄存器组的写入仍按各自效果处理。

寄存器映射依据 [Intel 8xC251Sx 用户手册](https://www.keil.com/dd/docs/datashts/intel/8xc251sx_um.pdf) 第 3-12～3-14 页；DATA 分配依据本仓库 `sdas/linksrc/lkarea.c`。硬件用 AI8051U 的实际 DATA 对象和高寄存器活值验证了这一路径。

父版 `d4a38c3`；四组采用相同源文件哈希、small/speed、正常 CMake 入口和默认调用反馈。

这一步净减少 137 B，最大单工程下降 1.70%。调用信息的覆盖面明显扩大，但直接体积收益有限，TFT 持平。它提供后续分配器使用的信息，不能据此宣布 120% 或 110% 目标完成。未测量与 Keil 同条件的运行时间。

## 验证和复现

`core/sources/compiler/src/mcs251/tests/check-object-call-effects.ps1` 通过 33 项检查：真实编译对象、extern 结构体及字段、同名 static、位对象、绝对地址、跨文件调用闭包、对象边界、物理寄存器别名、重复定义和 bank-0 分配条件。传入 `-Baseline` 可同时确认未启用反馈时，两份测试单元的 `.rel` 与父版完全相同。

实板固件由 `object-call-effects-hardware.c`、`object-call-effects-store.c`、`object-call-effects-user.c` 组成，AI8051U-34K64、40 MHz、UART1 P3.0/P3.1、115200 8N1。经 STC-Link1D 下载后，主机验证 1089 帧，覆盖 16 组边界输入、每组 3 个结果。普通后端调用省去 R2/R3 保存，宽后端跨文件调用省去 R12..R15、R24..R31 共 12 字节保存及对应恢复；被写的结构体位于 DATA `0x09`。可用 `check-object-call-hardware.py <uart.bin>` 复查串口记录。测试后保留该固件。

构建和串口指纹见 [object-call-effects-evidence.json](object-call-effects-evidence.json)。本机开发核心位于 `E:/STVAPP/MX251-mainline-20261109/object-effects/core-02/`，工程结果、测试输出和原始串口记录在同级目录。发行版本仍为 0.0170-test。
