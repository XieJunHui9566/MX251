# 按调用现场选择被调函数保留寄存器

2026-11-09，基于 `4a5702f`，实现提交 `3803d56`，分支 `codex/callee-preserved-registers`。本轮将部分寄存器的保存从多个调用现场移到被调函数入口/出口，作为显式构建选项。完整工程和实板原始记录、源输入与产物哈希见 [证据](callee-preserved-registers-evidence.json)。

## 完整工程结果

四项均沿用父版本的 SDK 输入、small/speed、函数共享、MachineIr、函数 GC 和普通调用反馈；仅增加 `CalleePreservation`。TFT/MSC 继续使用已有 NativeIntegerRuntime，两个 CDC 继续使用标准运行库。

| 工程 | 父版本 / B | 本轮 / B | 减少 / B |
| --- | ---: | ---: | ---: |
| p080 TFT | 21467 | 21304 | 163 |
| p087 USB CDC | 4597 | 4589 | 8 |
| p091 USB MSC | 5771 | 5765 | 6 |
| p095 USB 双 CDC | 6442 | 6424 | 18 |

TFT 的主要调用者变化：`gui_circle` 257→209 B，`LCD_DrawRectangle` 140→100 B，`Draw_Triangel` 121→88 B，`Show_Str` 741→716 B，`Fill_Triangel` 902→886 B。相应被调函数会变大，例如 `LCD_DrawLine` 180→184 B、`_draw_circle_8` 186→198 B；表中完整镜像已经计入这些成本。

三个 USB 工程均按同一规则选择 `usb_write_reg` 的 WR8 保留组，其本体 29→33 B，部分调用者省去重复保存。编译器和选择器没有 SDK 函数名或工程 ID 分支。

这是实际通用收益，但整工程降幅仍小。最佳体积台账仍为 **40 项 ≤120%，其中 18 项 ≤110%**；没有重跑完整 SDK，也没有新增完整工程双体积/运行时间达标记录。

## 实现

`CalleePreservation.ps1` 从已生成调用现场的 `mx251-call-effects` 提取实际保存组，扣除实参准备、返回值接收会覆盖的组，以及原调用写集合反馈本就能够省掉的保存。候选只包括具有唯一对象定义、已选择宽后端的普通函数。现阶段支持 WR8、DR12、DR24、DR28；不占用 A/B、返回窗口 DR4 或发射临时寄存器 DR16/DR20。

选择按静态保存指令字节估算，计入入口、各返回出口和尾调用变成普通调用的成本。它不使用执行频率，不保证全局最优，也不把估算作为最终收益。每单元生成带作用域的请求文件，编译器为被选函数发射 PUSH/POP；调用参数和返回值位置不变，栈参数的所有访问扣除新增入口保存字节，局部对象偏移仍相对局部帧。含保留组的函数使用普通返回路径，避免恢复覆盖原生 ABI 的实参。

这是额外保存行为，不是修改公开 ABI。请求文件本身也不是调用者的保留证明：后端选择仍可能采用 legacy。构建读取最终汇编，检查真实入口保存、控制流上的栈深度、原保存槽、全部返回路径的恢复顺序，然后从函数及其直接调用闭包的写集合中扣除已恢复的组。无法形成这项结论的函数不导出新保留事实；当前计算跳转表不参与此分析。普通和宽调用者继续消费既有反馈，最终逐调用核对实际省略的保存位。

物理机器指令优化同时将这些出口寄存器视为活值，保留恢复产生的值。递归和重入仍使用各自栈帧；本轮没有静态局部变量覆盖分配、参数打包 ABI 或运行库 ABI 迁移。

## 实板与验证

AI8051U-34K64，既有 40 MHz、Timer0 /12T、UART1 P3.0/P3.1、115200 8N1；自动找到 STC-Link1D 和 COM13。

矩形计时输入从 SDK 原样提取 `LCD_DrawLine`、`LCD_DrawRectangle`。像素输出改为独立的追踪回调，主机按原算法逐像素计算散列；这是绘图调用链内核，不是完整 TFT 刷屏时间。

| 用例 | 父版本 tick 总和 | 本轮 tick 总和 | 结果 |
| --- | ---: | ---: | --- |
| 矩形/直线调用链，64 个输入 | 36329 | 35380 | 时间减少 2.61% |
| 既有字节控制流，64 个输入 | 10188.5 | 10186 | 基本持平 |

每个输入取多帧中位数后汇总。父版 635 帧、本轮 604 帧，均通过 128 个结果检查，无 Timer0 溢出；固件 1440→1400 B。没有新建此内核的 Keil 时间分母。既有三角形用例没有选择保留组，新旧 HEX 完全一致，没有为它重复下载计时。

另用编译器级请求覆盖 WR8/DR12/DR24/DR28，重编已有调用边界夹具，检查取址形参、局部对象、栈实参、float/指针位运输、ABI2/ABI4 混用及真实中断现场。该固件 **128 个用例、255 帧全部通过**。这份测试使用 `preservation-replay.json` 绑定实际重编和链接命令及 HEX；原正常构建 receipt 对应重编之前的基线，不冒充新固件凭据。该夹具 Timer0 同时用作中断源，其 tick 不作为性能成绩。

其他检查：

- `check-callee-preserved.py`：small/large × speed/size 四组编译及汇编通过，包含递归和原生 ABI 的第二寄存器参数。
- `check-callee-preservation.ps1`：12 个控制流/栈恢复案例及 40 个实际编译函数通过；覆盖分支汇合、遗漏/错误恢复、保存槽覆盖、栈不平衡和未知 SP 改写。
- 四个完整工程均通过 `FINAL_ACTUAL_CALL_PRESERVATION_VERIFIED`。最终构建脚本复编 MSC 的 HEX 与前一脚本版本完全一致。
- 未开启新选项时，调用边界夹具 HEX 与父版本逐字节相同。

最后保留矩形计时固件，没有恢复旧固件。

## 使用与接续

```powershell
./Build.ps1 -ProjectPath E:/path/to/project -FunctionSharing -MachineIr -CalleePreservation
```

CMake 对应 `MX251_CALLEE_PRESERVATION=ON`，默认关闭。`NativeIntegerRuntime` 仍按原工程配置独立选择；新选项使用默认普通调用反馈，不与 `LeafCallFeedback` 同时启用。不要求修改 C 源文件或手工标注函数。

开发核心：`E:/STVAPP/MX251-mainline-20261109/callee-preserved/core-04`。编译器 SHA-256：`972b0eaac4bdacc8e50c397782767a50de7fed611b5476bdf5545bb75f609423`。此目录是开发编译器/构建脚本快照，不是发行包；编译器源码以本分支为准。`core-03` 使用相同编译器，最终脚本补齐了选项记录、冲突选项诊断和候选范围检查。

`tools/research/callee_preserved_fixture.py create --source <gui.c> --output <新目录>` 生成矩形夹具；`capture --hex <固件> --output <新目录>` 下载并核对原始串口。详细构建、未采用试验及实板记录均在同级研究目录。

这批结果进一步确认：只改保存位置仍不能填平 TFT 的主要差额。后续应接着处理参数栈、局部对象和活跃区间之间的搬运，复用现有保存事实；不通过继续枚举寄存器权重或默认开启所有保留组来凑收益。
