# 循环取负与原生十进制格式化

2026-11-10，实现提交 `126069e`，基于 `8e93c2f`，分支 `codex/loop-negate-format`。修改 MX251 后端选择及工具链格式化运行库，SDK 输入未改。

统一编译 **75/75 成功**；**25 项缩小、50 项相同、0 项变大，净减少 1329 B**。体积 ≤Keil 120% 为 **61 项**（原 59），≤110% 为 **49 项**（原 48）。总计 206511 / 192051 B，即 **107.53%**。这些是体积成绩，完整工程运行时间尚未测。

## 共性改动

- 循环中的 8/16 位无符号取负不再直接排除整个宽后端候选。复用既有完整函数比较：两份代码成本均已知、宽后端字节数更少且静态指令数不更多时才选择宽后端。导入、ABI、调用和寄存器规则不变；这不是动态周期上界。
- 私有整数格式化内核的 16 位十进制转换改用目标机原生字除法，替代逐位软件长除法。32 位转换保持原算法，避免引入额外长除法库。八进制和十六进制仍使用移位。
- 生成的格式化运行库继承项目的 MachineIr 开关，使用既有机器指令优化。公开 printf/sprintf 的变参 ABI、格式支持和启用条件不变。

没有按 SDK 工程名或函数名选择。75 工程中 185 份应用 REL 与父版逐字节相同，本轮矩阵收益全部来自 25 份生成的运行库。通用编译器能力另由 SDK 无关夹具验证：`loop_negate` 从 90 B 减到 53 B，包含循环中的 8/16 位模取负及回绕。

## 附加发现

large 模型附加夹具没有选中紧凑格式库，沿用完整 printf。混合 `%bd/%bu` 与普通 C 提升参数时，父版和新版均有完全相同的 58/128 项差异，全部在 16 位格式组；32 位/循环组两版均通过。源码中完整格式库对 b 转换按 `va_arg(ap,char)` 取 1 字节，调用方传入 2 字节。记录为既有兼容性问题，未计入本轮通过项，也未为本轮优化扩改该库。

曾检查 10 个包含纯数据 C 单元的工程是否能启用紧凑格式化。实际均没有格式调用，没有收益，撤回试改；避免为了覆盖标记增加无效改动。
