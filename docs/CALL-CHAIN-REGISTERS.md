# 调用者需求驱动寄存器分配：原型收益不足

2026-11-09，从 `a1b9f9e` 开始。已经完成一个显式原型和两个代表工程的完整构建：**TFT 持平，USB MSC 减少 10 B（0.16%）**。停止扩展这一版寄存器偏好方案，编译器与构建入口恢复父版。SDK 未修改，没有下载硬件或重跑 SDK 大矩阵。

| 工程 | 父版 / B | 原型 / B | 变化 / B |
| --- | ---: | ---: | ---: |
| p080 TFT | 22093 | 22093 | 0 |
| p091 USB MSC | 6312 | 6302 | −10 |

两侧均开启已有函数共享和函数 GC，使用相同 small/speed 配置、标准运行库、512/2048 宽后端容量。源文件哈希和工程快照相同，最终 ASM/RST 与 HEX 核对通过，两个 GC 图均闭合、无回退。构建标识和哈希见 [证据](call-chain-registers-evidence.json)。这些是体积结果，不是执行正确性或 Keil 运行时间达标结论。

## 实现了什么

[筛选工具](../tools/research/call_register_costs.py)从最终构建的调用现场元数据提取跨调用活跃寄存器，扣除实参准备和返回接收的固定写入。对于具有唯一导出 ABI2 定义、已有写集合反馈且实际选择宽后端的函数，按当前保存冲突组数与函数指令数的比值排序，每个工程选择一个目标。没有 SDK 函数名特判。

原型为目标函数读取 32 个物理字节的调用者需求成本；在原冲突图、寄存器候选集合和 ABI 固定位置下，优先使用需求较低的寄存器，同成本时继续使用已有调用感知选择。它没有新增保存/恢复语义，也没有宣称偏好文件能证明寄存器被保留。完整构建重新分析实际写集合、重编调用者，沿用原有最终调用保存核对。

自动选择的是 p080 的 `LCD_DrawLine`（7 个宽后端调用现场、18 组相关保存冲突）和 p091 的 `usb_write_reg`（32 个宽后端调用现场、2 组相关保存冲突）。现场数量是静态数量，不是运行频次，也不包括所有旧后端调用。

## 为什么没有大收益

- **TFT 的分配确实改变了，但调用破坏集合没有缩小。** `LCD_DrawLine` 中多个值改用了其他物理寄存器，仍有四个值落栈、5 B 溢出帧；调用闭包写集合前后都是 `ff33ffff`。现有整函数分配在不同位置仍会使用这些寄存器，重新排列位置并没有为调用者腾出可贯穿调用的寄存器。
- **USB 确实消除了两组保存，但覆盖已经很小。** `usb_write_reg` 的写集合由 `00000b00` 变为 `00000904`，让出 R9。`usb_in_ep1`、`usb_out_ep1` 各减少 4 B，`usb_set_address` 通过随后的调用反馈与分配减少 2 B；被调用函数自身体积不变。

这次否定的是“依据静态调用者需求，调整单个被调函数的整函数寄存器偏好，就能取得大收益”的简化方案。**没有实现或否定同时优化整张调用图的分配器。** 输入也未包含旧后端调用者的完整活跃需求，因此不能把这个排序当作全局最优选择。

若继续寄存器方向，新的机制应允许同一个值在不同区段采用不同位置，或把发射器临时寄存器纳入分配；仅增加偏好权重、轮数或更多候选，不解决本轮看到的占用问题。此前调查已发现三个 USB 工程的已选宽后端没有值溢出，所以活跃区间拆分仍不能预先承诺普遍大收益。

另外，p091 的私有 `shift` 已被现有汇编分析识别为只写 `00000880`，但当前反馈只绑定导出定义，调用者仍使用未知目标的保存方式。这是单独的文件作用域绑定缺口，不是本轮寄存器协同的收益，未混入上述结果。
