# 剩余 11 个工程的体积归因

2026-11-10，研究基线为 `ordinary-bits/core-04`（实现 `f5f1c52`，保存点 `76ff7c7`）。统一 75 工程仍是 **64 项 ≤120%、50 项 ≤110%**。本轮只读取已有成品、编译器实现和历史证据，新增研究脚本与记录；没有修改编译器、SDK，没有重新编译或操作硬件。

结论：先解决**既有优化与原生 ABI4 调用的衔接缺口**，再扩展**中断现场保存与指令效果分析**。除法库体积策略、循环地址生成与分支共用尾部也有明确差距。p108 应单独处理原始数值向量与完整格式库问题。无需为这 11 项先推倒整个编译器。

## 第一优先：让已有优化在组合版本中生效

旧的 [窄无符号取负](NARROW-NEGATE.md) 已解决过波特率计算中 `65536 - value` 化成 16 位取负后整函数退回字节后端的问题。本轮读取旧 ASM/RST/HEX，确认 p087/p095 的 `uart_set_baud` 当时为 **349/475 B**，当前为 **474/616 B**；两份 `uart.c` 内容哈希分别与当前相同。旧版没有当前全部构建机制，这 266 B 历史函数差额不是新版本的实测可恢复收益，但明确说明能力曾经存在。

当前有两个具体衔接点：

1. `backend_choice.c.inc:mcs251BackendChoiceEligible` 只在含有序内联操作时接受 ABI4 调用。`mcs251BackendNarrowTrial` 依赖这条资格检查；p087 的普通函数调用原生 ABI4 `__divulong`，窄取负候选因而没有进入。最终诊断在 `wide.c` 的窄无符号 UNARYMINUS 导入处退出，回到字节后端。
2. p095 的 `uart_set_baud`、`uart_init` 在真实对象参数快照送入 ABI4 时退出，最终诊断为 `argument-snapshot-abi4-contract`。这是实参求值和调用表达能力的缺口，不能只放开前一条资格判断。

后果可直接看见：p087 的 14 个 32 位 switch 值产生 **224 B CJNE**；Keil 使用原生宽减法/比较链并共享部分赋值尾部。p095 对应函数有 **166 B CJNE** 和 64 B PUSH/POP。先贯通现有宽后端、实参快照与整数运行库调用，再看剩余 switch 布局差距，比另起一个 switch 专项更合算。

后续实现依据函数类型、调用约定和求值顺序，不按这里的函数名选择。先用这两份冻结输入观察候选能否生成及完整镜像净变化，再决定扩展范围。

## 第二优先：中断保存和函数体的原生操作

这批 10 个含中断的工程共 16 个 C ISR，MX 入口/出口 PUSH/POP 编码共 **852 B**；Keil 列表中对应 ISR 的全部 PUSH/POP 共 **420 B**。同名 ISR 的完整函数差额合计 **825 B**。这些是现存开销，包含必需保存，不能承诺全部消除。

上轮已处理外设位写入，但仍有不同阶段没有贯通：

- `gen.c:usePackedIsrContext` 遇到任何 INLINEASM 仍退出打包保存。p049 的已知外设位操作、p136 的中断体仍保留 104 B 保存序列，而普通打包全保存序列是 56 B。48 B 是两种现有序列的编码差，不是这两个函数已验证的节省。
- 保存分析不认识部分正常参数栈指令。p049 首次停在 `pushw #0x0002`，p051 停在 `dec spx,#2`。需把实参压栈、清栈和调用效果连成一体；不能孤立删除栈操作。
- p087/p095 的 USB ISR 在 `_usb_setup` 调用处退出，调用图的效果信息还不完整。
- p136 首次停在 `_ADC_RESL`（地址 0xBE）；当前公共指令模型将该地址列为核心状态。后续需要明确目标寄存器映射，再给出对应效果，不能全局把这个地址当普通内存。
- p045 的 LVDF 位位于 PCON 低六位，当前按核心状态处理；它与普通外设位并非同一种情况。
- ISR 整体仍跳过宽后端入口，p051 中 16 位增减/比较拆成字节指令。长期可复用普通函数的原生函数体，再由中断入口封装现场；不必一次重写全部入口。

p047 展示了另一条链：Keil 用 `MOV C,CMPRES` 再写输出位，MX 则读取 A、掩码、算术转成 C，连带增加 A/PSW 保存和 bank 设置。这属于通用位值降低；不要用修改 SDK 表达式绕过它。

## 第三层：除法库、寻址与分支尾部

**整数库。** p013/p087/p095 都链接原生无符号长除法成员，213 B 对 Keil 的 83 B，每个镜像相差 130 B。p013 中它占总差额的 80%，只优化 main 几乎解决不了该项。p013 的 Keil 调用为 `?C?ULIDIV`，除数 16000；两个 CDC 的默认计算用 `?C?ULDIV`，除数可以是完整 32 位，不能都按 16 位处理。

现有 213 B 库含已验证的多种快速路径并同时提供余数。下一步应研究紧凑基础例程与按操作数范围选用的快路径如何组织，或编译器如何选择窄除数入口。不能只为缩体积删掉快路径而忽略最终运行时间目标；[已有整数优化及实板结果](NATIVE-INTEGER-OPTIMIZATION.md)继续有效。

**地址与值运输。** p074 的两个复制循环反复执行基址复制、索引零扩展、32 位相加、24 位掩码，再装入 DPX 读取字节。p136 的 PlayProcess/main 同样有符号地址构造、指针运输、字节拼接与较长分支。常量数据体积相同，差距在生成代码。已有 CODE 原生读取只覆盖 16/32 位；此前直接全面替换字节读取会让完整工程增大，见 [CODE 读取记录](NATIVE-CODE-READS.md)。应组合循环游标/地址降低后做整函数比较，不能重跑那次全面替换。

**分支共同尾部。** p095 的 SetMCLK 为 369/196 B：Keil 多个分支共用读取校准值、写 IRCBAND、恢复分频、更新 MAIN_Fosc 的尾部；MX 多次物化地址/常量并复制这些操作。项目已有尾部合并实现，后续关注寄存器值不同但操作相同的分支能否先归一化，再合并。仅把当前选择从 wide 369 B 换成 legacy 365 B 只省 4 B，不值得作为主线。

## 启动/向量差额与 p108

p047/p074/p136 分别保留 21/58/61 个未使用中断槽的单字节 RETI。这里统计的是实际 HEX 字节，`.ds` 的空洞没有被算进去。Keil 的输出不包含同样的默认槽，所以小工程比例会明显受影响。默认异常中断处理行为有差别，不把去掉 RETI 当作无条件等价优化。

p149 的 GSINIT4 为 36 B，包含清 DATA 与 XDATA；Keil 启动段较小。是否存在启动清零后在首次读取前必定覆写的对象，可另作通用初始化消除，但只为该工程最后 2 B 不值得展开研究。

p108 的当前报告同时是 `FALLBACK_FULL_RUNTIME` 和 `FALLBACK_FULL_STARTUP`，原因为 `format-raw-jump-outside-registered-vector`，链接了 `vprintf`、`printf_large`、乘法及通用指针辅助成员。

旧证据引用目录已不在本机，本轮用冻结 Keil 成品重建了核对：原始 `isr.asm` 末端跳到 `0x006B`，Keil 最终 `0xFF01DD` 的字节为 `02 00 6B`；main 位于 `0xFF0026..0xFF00EE`。目标 `0xFF006B` 甚至落在 `0xFF0069` 的三字节 `MOV DPL,R7` 的第三字节。它不是可直接登记的 C ISR 入口。

保持它在 75 项原始台账中，不把 64/75 改成另一个分母。后续可独立研究无须依赖全程序闭合的通用小型格式库，或解决绝对地址向量的可重定位表达；本轮不改原输入、不把引用问题伪装成已过线。
